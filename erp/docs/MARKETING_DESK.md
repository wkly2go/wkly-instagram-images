# 광고 메뉴 · 캠페인 준비

기존 광고 메뉴의 `/ads?tab=studio`에서 캠페인 기획, 계획 예산, 문구, 사진 소재와 검토 기록을 관리한다. 기존 광고 성과·캠페인·소재·보고서 표와 기록은 변경하지 않는다.

## 광고 메뉴 탐색

- **대시보드:** 선택 기간의 성과, 최근 일일 보고, 접어 두는 캠페인 확인 목록.
- **캠페인 준비:** 기획·예산 → 문구·소재 → 검토·집행자료의 3단계 작성.
- **성과·보고서:** 매체별 성과, 추이 그래프, 일별 수치, 일일 보고.
- **소재·리서치:** 우리 소재 검색, 경쟁사 분석, 해외 사례.
- **검색 노출:** 기존 SEO·AEO·GEO 점검.

기존 `tab`과 보고서 `id` 링크는 유지한다. 성과 조회 기간(`period`)과 매체(`platform`)도 주소에 남아 뒤로 가기와 새로고침에 유지된다. 기간은 한국 날짜 기준 어제까지이며, 이번 달 비교도 직전의 같은 일수로 계산한다. 기록이 없는 기간은 0원으로 표시하지 않고 빈 상태를 안내한다. 매체별 화면의 캠페인 상태·계획 예산은 성과 기록이 없어도 확인할 수 있다. 조회 실패에는 재시도 안내가 표시된다.

보고서는 광고 본문에서 읽고, 본문이 좁으면 목록을 선택 상자로 전환한다. 화면 배치는 채팅 칸을 제외한 실제 본문 폭에 맞춘다.

## 사용 순서

1. 관리자 계정으로 **광고 → 캠페인 준비 → 새 캠페인**을 연다.
2. 브랜드·채널·목표·연결 주소·기간·계획 예산을 입력하고 초안을 저장한다. 예산을 모르는 단계에서는 비워 둘 수 있다.
3. 문구를 편집하고 JPEG·PNG·WebP 사진을 올린다. 이미지 한 장의 제한은 8MB이다. 네이버 검색광고는 텍스트 광고 확인으로 이미지 없이 준비할 수 있다.
4. 변경 내용을 저장한 뒤 문구·소재 사용 권리·예산을 검토하고 준비 완료로 저장한다. 검토 대상 내용이나 사진이 바뀌면 관련 확인은 다시 필요하다.
5. TXT·JSON 준비 자료와 이미지 원본을 내려받고 해당 광고 관리자에서 최종 등록한다.

캠페인 목록은 **캠페인 목록 → 변경**에서 펼친다. 작성 중에는 상단의 저장·이전·다음 작업바가 따라 내려온다. **준비 현황**의 항목을 누르면 해당 입력 위치로 이동하며, **광고 미리보기**와 **시즌·이벤트 / 참고 자료**는 필요할 때 펼친다. 저장 전 메뉴 이동이나 캠페인 변경에는 미저장 확인이 표시된다.

준비 완료는 사내 검토 상태이다. 다운로드·광고 관리자 열기는 매체 등록, 실제 게재 또는 비용 집행을 뜻하지 않는다. 실제 성과와 지출은 기존 보고서 탭에서 확인한다.

문구 예시는 고정 템플릿이다. **AI 기획 요청 복사**는 현재 입력한 자료로 요청문을 만든다. 이 기능 자체는 생성 모델이나 광고 API를 호출하지 않는다. 시즌·이벤트 메모는 기획 요청과 전달 자료에 포함된다.

## 공용 저장과 권한

- 운영: 기존 Supabase 로그인, `marketing_campaigns`, `marketing_assets`, 비공개 `marketing-assets` 저장소.
- 활성 관리자: 캠페인 작성·수정, 소재 업로드·연결 해제.
- 활성 일반 팀원: 캠페인과 소재 조회. 데이터베이스와 저장소에서도 같은 제한을 적용한다.
- 비활성·로그아웃 사용자: 접근 불가.
- 저장 버전이 다른 수정은 거부한다. 다른 관리자가 수정했을 때는 목록을 다시 불러오고 변경 내용을 확인한다.
- 이미지 주소는 1시간짜리 서명 주소이다. 공개 저장소를 만들지 않는다.
- 체험 모드: 브라우저의 별도 IndexedDB에만 저장한다. 운영 데이터로 옮겨지지 않는다.

운영 저장 실패 시 기기 저장으로 바꾸거나 성공으로 표시하지 않는다. DB 적용 전에는 공용 저장소 준비 안내가 표시된다.

## 기존 독립 앱 백업 이전

독립 앱의 **설정 → 백업 내려받기**로 받은 버전 1 JSON을 선택한다. 미리보기 후 가져오면 캠페인과 연결된 이미지를 새로운 공용 초안으로 저장한다. 기존 캠페인을 덮어쓰지 않으며 검토 확인은 초기화한다.

이미 연결된 공용 데이터를 백업 파일의 ID로 덮어쓰지 않는다. 순차 이전 중 실패한 작업은 화면에 남은 진행 상태에서 이어갈 수 있다. 페이지를 닫고 같은 백업을 다시 가져오면 새 초안이 추가될 수 있으므로, 기존에 가져온 목록을 먼저 확인한다.

백업의 성과·설정·작업 기록과 캠페인에 연결되지 않은 소재는 이전하지 않는다. 원본 백업은 따로 보관한다.

## 설치·배포

1. 대상 프로젝트가 `hophgcpszenrvchvbkav`인지 확인한다.
2. `supabase/migrations/0107_marketing_desk.sql`을 해당 프로젝트에 **한 번** 적용한다. 기존 0001~0106 마이그레이션이 적용된 환경을 전제로 한다. 파일은 새 표·함수·비공개 저장소만 추가하며 트랜잭션 안에서 실행한다.
3. 관리자·일반 팀원 계정으로 캠페인 저장과 읽기 권한을 확인한다. 실제 운영 확인에는 별도 확인용 초안을 사용한다.
4. 웹 변경을 검증한 뒤 기존 Cloudflare Pages 배포 흐름으로 반영한다.
5. 기존 PC 앱은 같은 웹 주소를 읽으므로 웹 업데이트를 반영한다. 이 변경은 Electron 패키지나 서비스 워커를 추가하지 않는다.

SQL 파일이 저장소에 있다고 DB에 적용된 것은 아니다. 실제 적용과 운영 저장 확인 전에는 설치 완료로 기록하지 않는다. 이 기능에는 새 Edge Function 배포나 서비스 역할 키가 필요하지 않다. 비밀 키·토큰·비밀번호를 소스 또는 대화에 넣지 않는다.

## 검증

```bash
cd erp
npm ci
npm run test:marketing
npx tsc --noEmit -p .
npm run build
VITE_SUPABASE_URL= VITE_SUPABASE_ANON_KEY= npx vite --host 127.0.0.1 --port 5179
```

테스트 명령은 Node 22.18 이상을 사용한다. 조회 기간의 월·연 경계/윤년/월초 빈 기간/매체 필터/0값 보존, 캠페인 순수 로직과 로컬 PostgreSQL 엔진의 DB 권한·변경 버전·검토 초기화를 검사한다. DB 테스트는 운영 DB에 접속하지 않으며 Supabase Storage의 실제 HTTP 업로드를 검증하는 것은 아니다.

화면 확인은 **관리자 (대표)로 입장**하는 체험 모드에서 저장·재접속·이미지·다운로드를 확인하고, 일반 팀원으로 다시 들어가 쓰기 버튼과 수정 권한을 확인한다. 기존 요약·성과 보고서도 열어 본다.
