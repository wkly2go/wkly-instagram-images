# 능력 지표 — 재는 법

2026-11-19 대표 지시 '현제 인트라넷 능력을 정량화하고 개선 사항 제안해' → '모든 수치가 80이상이 나오도록'.

아침 보고의 점수는 사람이 매긴 추정이었습니다. 숫자를 꾸미지 않도록 **계산식**으로 바꿨습니다.
서버가 매일 00:05(KST)에 재서 `private.capability_daily` 에 남기고, 관리 › '능력 지표'에서 봅니다.
계산은 `supabase/migrations/20261119212000_capability_score.sql` 의 `private.capability_measure()` — 이 문서와 같아야 합니다(바꾸면 둘 다).

## 원칙

- 축 점수 = 세부 지표 점수의 평균 · 종합 = 일곱 축의 평균 · 목표 80점
- 세부 지표는 '기준선 사이를 곧게 이은 값'(예: 첫 화면 250KB 이하 100점 · 350KB 70점 · 500KB 40점)
- 기준선은 점수를 재기 **전에** 정했고, 점수를 올리려고 기준선을 바꾸지 않습니다. 바꿀 일이 생기면 이유를 이 문서에 적습니다.
- 사람이 정해야 하는 값은 두 가지뿐: 기능 목록의 완성 · 부분 · 아직(`app_settings.capability_features`), 대표가 대시보드에서 켜는 보안 설정(`security_flags`)

## 아침 추정과 달라진 것 (정직하게 적어 둠)

- **자동화**: 아침에는 '전체 일지 중 자동으로 적힌 줄의 비중'(3%)과 '모든 메일 중 프로젝트에 붙은 비중'(44%)을 썼습니다.
  일지는 사람이 직접 쓰는 글이 많을수록 낮게 나오고, 메일은 깃허브 · 구글 같은 서비스 알림이 섞여 있어 자동화의 뜻과 맞지 않았습니다.
  그래서 '끝낸 할 일이 일지에 자동으로 남는 비율'과 '거래 메일(사내 · 서비스 알림 제외) 중 프로젝트에 붙은 비율'로 바꿨습니다.
- **실사용**: 아침에는 '꾸준히 쓰는 기능 11/25'만 봤습니다. 지금은 조금 쓰는 기능에 0.5점을 주고, 쓴 사람 · 알림 읽음 · 지연 비율을 함께 봅니다.
- 이 때문에 같은 날에도 숫자가 달라집니다. 앞으로는 이 계산식 하나로만 견줍니다.

## 오늘 바로 오르지 않는 것

- **안정성**의 '마지막 장애 뒤 지난 날'은 날이 지나야 오릅니다(11/19 장애 → 7일 뒤 80점 · 14일 뒤 100점).
- **실사용**은 팀이 실제로 써야 오릅니다. 인트라넷이 할 수 있는 것은 누르기만 하면 되게 만드는 것(주간 보고 초안 · 알림 줄이기 · 메뉴별 사용법)까지입니다.
- **보안**의 '유출된 비밀번호 거르기'는 대표가 Supabase 대시보드(Authentication › Sign In / Providers › Password)에서 켭니다. 켠 뒤
  `app_settings.security_flags` 의 `leaked_password_protection` 을 true 로 바꿉니다.
- **백업 복구 확인**은 Supabase 대시보드(Database › Backups)에서 백업 목록을 확인한 날을 `app_settings.backup_checked` `{"at": "…"}` 로 적습니다.

## 빌드 값

첫 화면 묶음 크기 · 시험 수 · 설명서 수는 서버가 알 수 없어, 빌드가 `version.json` 의 `stats` 에 적고(`vite.config.ts`) 관리자가 관리 화면을 열 때 서버로 넘깁니다.
손으로 확인: `npm run build && npm run check:bundle`
