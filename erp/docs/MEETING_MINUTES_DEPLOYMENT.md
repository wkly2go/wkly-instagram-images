# 회의록 서버 함수 배포·복구 안내

> **2026-11-13 갱신:** `meeting-minutes` 운영 배포와 코드 일치, JWT ON 유지, GET 405를 확인했습니다. 아래 11/12 배포 대기 문구는 과거 기록입니다. 실제 생성·원본 정리는 실행하지 않았습니다. [최신 배포 기록](SERVER_DEPLOYMENT_20261113.md)을 우선합니다.

2026-11-12 로컬 검증 완료·서버 배포 대기 기록입니다. 함수 이름은 **`meeting-minutes`**입니다. PR #367의 웹 배포와 단일 파일 준비는 완료됐지만, **Supabase 함수의 별도 배포·운영 호출은 확인되지 않았습니다.** 이후 상태는 해당 변경의 검사 결과와 함수 배포 기록을 우선 확인합니다.

외부에서 받아쓴 텍스트를 Claude로 회의록 초안으로 정리합니다. 음성 직접 받아쓰기는 지원하지 않으며 API 비용은 별도입니다. 이번 후속 수정은 동시 시작·불확실한 응답·완료 저장·원본 경로 확인을 보완합니다. DB 설치나 예산 변경은 하지 않으며 실제 유료 호출 없이 로컬 검증합니다.

## 1. 원본과 배포물 확인

`erp` 디렉터리에서 실행합니다.

```sh
npm run build:meeting-dashboard
node scripts/build-meeting-minutes-dashboard.mjs --check
npm run test:meeting
node --experimental-strip-types --test tests/meeting-processing.test.mjs tests/meeting-progress.test.ts
```

- 원본: `supabase/functions/meeting-minutes/cleanup.ts`, `index.ts`
- 생성 파일: [`supabase/deploy/meeting-minutes-dashboard.ts`](../supabase/deploy/meeting-minutes-dashboard.ts)
- 생성기는 원본 SHA-256을 기록하고 내부 import를 합칩니다. 원본 수정 후 재생성하며 배포물만 직접 고치지 않습니다. `--check`가 실패하면 배포하지 않습니다.
- 서버 동작은 모의 SDK와 로컬 PGlite의 실제 테이블 스키마로 검사합니다. 웹의 시간 제한·동일 기록 재조회 검사를 추가했고 실제 React DOM 회귀 검사 14/14가 통과했습니다. 전체 회귀 291/291 및 별도 React DOM 14/14, TypeScript·빌드·서버 원본/배포본 Deno 검사 통과를 확인했습니다. 이를 Supabase 런타임·실제 계정 검증으로 대신하지 않습니다.

## 2. 처리 중복·불확실성 처리

| 상황 | 보완한 동작 |
|---|---|
| 동시에 같은 기록 시작 | 기존 상태·수정 시각이 맞는 행만 고유 처리 표식으로 선점합니다. 선점이 확인된 요청만 AI를 호출합니다. |
| 이미 완료 또는 처리 중 | 현재 상태를 반환하며 AI를 다시 호출하지 않습니다. 지난 시간만으로 처리 중 기록을 재선점하지 않습니다. |
| AI 호출 전 확정 실패 | 입력·파일·설정 확인 실패를 해당 선점 기록에만 남깁니다. |
| AI 호출 후 응답·파싱·저장 불확실 | `MEETING_REVIEW:` 안내와 처리 중 상태를 유지합니다. SDK 자동 재시도를 끄고 다른 요청의 기록을 덮어쓰지 않습니다. |
| 완료 저장 응답 유실 | 같은 기록에 저장된 완료 상태·회의록·원문이 일치할 때만 완료로 확인합니다. 확인 불가 시 검토 상태를 유지합니다. |
| 원본 정리 | 회의록 결과 저장 완료가 확인된 처리 뒤에 정리를 실행합니다. 삭제 후보는 **현재 완료 상태이며 생성일(created_at) 기준 30일이 지난 기록**입니다. 완료된 날부터 30일을 계산하지 않습니다. 실패·업로드·처리 중 원본은 보존합니다. |

원본 읽기·정리는 해당 작성자의 업로드 경로인지 검사합니다. 다른 작성자 경로·상위 경로 이동·허용되지 않은 경로 표시는 거부합니다. 정리할 파일을 참조하는 모든 기록도 완료 상태·생성 후 30일 경과·소유 경로 조건을 만족해야 합니다. 참조에 실패·업로드·처리 중 기록이 하나라도 있거나 조회가 불완전하면 파일을 보존합니다.

## 3. 화면이 오래 기다리거나 응답을 잃었을 때

1. 서버 호출 접수 응답이 30초 안에 확인되지 않으면 화면은 **접수 여부 불확실**로 안내하고 원래 기록 ID를 보존합니다. 시간 초과가 서버 작업 취소를 뜻하지 않습니다.
2. 접수 뒤에는 같은 ID만 주기적으로 읽습니다. 개별 조회가 멈춰도 독립적인 20분 제한에서 화면 대기를 끝냅니다. 늦게 도착한 응답이나 닫힌 화면의 결과는 반영하지 않습니다.
3. 불확실한 상태에서는 새 녹음·업로드를 막습니다. **같은 기록의 상태만 다시 확인**을 누르면 해당 ID를 읽을 뿐 AI 생성이나 파일 업로드를 다시 실행하지 않습니다.
4. `MEETING_REVIEW:` 또는 계속 처리 중인 기록은 관리자에게 **기록 ID와 오류 종류만** 전달합니다. 원문·키·전체 로그를 채팅이나 공개 문서에 붙이지 않습니다.
5. 관리자는 권한 있는 화면에서 현재 상태와 저장된 결과, 제공자 처리 여부를 확인합니다. 상태를 임의로 실패·업로드로 되돌리거나 새 ID로 다시 요청하지 않습니다. DB 장애로 결과가 저장되지 않았다면 원래 AI 응답을 자동 복구할 수 있다는 보장은 없습니다. 추가 생성이 필요하면 비용과 원본 보관을 확인한 별도 작업으로 처리합니다.

`meeting-minutes`는 `growth-ai`의 기간 한도·사용 기록에 연결되어 있지 않습니다. 인트라넷 AI 사용·비용 화면의 한도를 이 함수의 한도로 해석하지 않습니다.

## 4. 별도 서버 배포

1. Supabase 대상 프로젝트와 기존 **meeting-minutes**의 현재 버전을 확인합니다. 다른 함수는 교체하지 않습니다.
2. 대시보드 `index.ts`에 생성 파일 **전체**를 적용합니다. 원본 `index.ts`만 넣으면 `cleanup.ts` 의존성이 빠집니다. 인증된 CLI를 사용한다면 원본 파일 전체를 함께 배포합니다.
3. JWT 검증을 유지합니다. `ANTHROPIC_API_KEY`와 Supabase 기본 환경값은 존재 여부만 확인하고 값을 코드·채팅·캡처에 넣지 않습니다.
4. 함수 이름·배포 성공·시점을 확인합니다. 웹 배포만 완료한 경우 서버 적용 완료로 보고하지 않습니다.

**0107 및 성공한 0113·0114·0115를 재실행하지 않습니다.** 기존 회의 SQL도 이력 누락만으로 실행하거나 전체 `db push`를 하지 않습니다.

## 5. 운영 확인과 보관 제약

비용 없는 메서드·로그인 차단 경로부터 확인합니다. 함수 본문에 도달한 OPTIONS는 200, GET은 405, Authorization 없는 POST는 401입니다. 플랫폼 JWT 차단이 먼저 발생해도 이를 피하려고 인증을 끄지 않습니다. 이 경로는 AI·Storage·DB 쓰기를 시작하지 않는지 로컬에서 검사합니다.

실제 기록 ID로 생성 시험을 하거나 회의록 작성 버튼을 누르는 것은 별도 작업입니다. 정상 경로는 Claude 비용을 발생시키고, 결과 저장 완료 뒤 현재 완료 상태이면서 생성일 기준 30일이 지난 기록의 원본을 정리할 수 있습니다. 이번 개발에서는 운영 생성·정리·유료 호출을 실행하지 않았습니다.

정리는 최대 50건의 기존 후보를 확인하며 정기 예약이 아닙니다. 정확히 30일에 삭제되거나 배포 직후 저장량이 감소한다고 보장하지 않습니다. 공유 참조에 보호 대상이 있으면 파일을 보존하며 실패·업로드·처리 중 원본은 삭제하지 않습니다. 파일 삭제 실패 시 참조를 유지합니다. 관리자·작성자 권한, 실제 텍스트 업로드·완료 저장·모바일 동선은 별도 운영 확인이 필요합니다.

조직 Usage·Storage·Egress 수치는 확인 전입니다. [용량 점검 안내](SUPABASE_CAPACITY_OPTIMIZATION.md)에 따라 같은 기간을 비교하며, 코드·로컬 테스트 완료를 과금 경고 해제로 보고하지 않습니다.
