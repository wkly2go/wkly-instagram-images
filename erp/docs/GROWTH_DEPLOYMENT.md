# 영업·콘텐츠 확장 운영 적용 순서

대상 프로젝트: `hophgcpszenrvchvbkav`. PR #354는 main `1f18364c7f18e4f7e204acee31326e7d439956d9`에 병합되었고 Cloudflare 운영 배포 체크 성공을 확인했습니다(https://3912a145.wkly-erp.pages.dev). 사용자가 0113·0114·0115 설치 성공과 설치 후 9항목 정상 화면, growth-ai 로그인 차단 응답, 로그인한 앱에서 Haiku의 `연결 성공` 및 완료 비용 안내 화면을 제공했습니다. 따라서 아래 설치·초기 시험 절차는 이미 수행한 이력과 향후 참조용입니다.

**0107 및 0113·0114·0115 재실행 금지.** 현재 비용 표시·실행 기록 자동 갱신 보완은 로컬 검증 완료·웹 배포 대기 단계이며 DB 변경이나 growth-ai 재배포가 필요하지 않습니다. 사용자 시험의 `$0.0000`은 네 자리 반올림 표시로 무료를 뜻하지 않습니다. 이번 보완에서는 추가 유료 AI 호출, 예산 증액, 예약액 초기화를 하지 않습니다. 전체 진행률은 약 92% 추정이며 실제 역할별 저장·모바일 동선, 외부 계정 연동, meeting-minutes와 조직 사용량 확인이 남아 있습니다.

최신 main의 다른 변경을 보존합니다. 이번 웹 보완은 비용 표시 2개를 포함한 169/169 테스트, TypeScript 검사, Vite 프로덕션 빌드가 통과했습니다. 기존 큰 번들·정적/동적 import 경고는 유지됩니다. DOM 테스트 환경이 없어 React 동기화는 코드 검토로 확인했으며 운영 화면 재검증과 배포 성공 확인은 남아 있습니다. 변경 없는 서버의 이전 Deno 결과와 구분합니다.

## 1. 지금 확인할 항목 — 변경 없이 조회

Supabase 대상 프로젝트의 **SQL Editor → 새 쿼리**에서 다음 파일의 내용을 실행합니다.

`erp/supabase/diagnostics/growth_preflight_readonly.sql`

이 쿼리는 기반/신규 테이블, 서버 함수, 메일 자동 후보 트리거, 설치 이력 테이블의 존재만 확인합니다. 고객·메일 본문·비밀 키를 읽거나 데이터를 변경하지 않습니다. 설치 전·후 DB에서 읽기 전용 트랜잭션으로 검증했습니다.

- 기반 테이블이 모두 있어야 합니다. 일부가 없으면 해당 선행 기능의 설치 상태를 확인합니다.
- 신규 테이블이 모두 없으면 새 기능 미설치 후보입니다. 실제 이력을 함께 확인합니다.
- 신규 테이블 일부만 있으면 부분 적용 또는 다른 세션 작업 가능성이 있으므로 같은 SQL을 바로 재실행하지 않습니다.
- 모두 있어도 정책·함수 정의가 일치하는지 확인해야 하며 존재만으로 배포 완료로 판단하지 않습니다.

설치 이력 테이블이 '있음'인 경우 별도 쿼리로 최근 이력을 확인합니다.

```sql
select version, name
from supabase_migrations.schema_migrations
order by version desc
limit 15;
```

SQL Editor에서 수동 적용한 변경은 migration 이력에 없을 수 있습니다. 이력이 없다는 이유만으로 과거 파일을 재실행하지 않습니다. **0107 재실행 금지.**

## 2. 필요한 DB 변경만 순서대로 적용

실제 이력·객체 정의와 최신 main을 비교한 후, 아직 적용되지 않은 아래 세 파일만 처리합니다.

1. `0113_sales_pipeline.sql`
2. `0114_growth_workspace.sql`
3. `0115_growth_ai_budget.sql`

현재 위치는 **DB·growth-ai·운영 웹 적용 및 사용자 Haiku 시험 성공 후 웹 사용성 보완**입니다. 성공 보고를 받은 0113·0114·0115를 다시 실행하지 않습니다. SQL Editor의 수동 실행 성공이 migration 이력 자동 등록을 뜻하지 않으므로 캡처·파일명·적용 상태를 체크포인트에 함께 기록합니다.

`supabase/diagnostics/growth_postflight_readonly.sql`을 새 쿼리에서 실행하면 9행 결과가 나옵니다. 신규 테이블 8개, RLS 8개, 팀원 조회 정책 8개, 비로그인 테이블 접근 차단 8개, 팀원 조회 권한 8개, 팀원 직접 변경 차단 8개, 필수 DB 함수 11개, AI 예약/정산 서버 전용 권한 2개, 메일 트리거 2개를 확인합니다. 데이터/키는 조회하거나 변경하지 않습니다. 전부 정상이어도 함수 본문 전체 일치나 실제 사용 동작을 증명하지 않으므로 앱 검증은 별도로 진행합니다.

각 파일은 트랜잭션으로 묶여 있습니다. 앞 파일 성공을 확인한 후 다음 파일로 진행합니다. 실패한 파일은 오류 원인을 확인하며 `DROP`이나 강제 재생성으로 해결하지 않습니다. 이력 불일치 상태에서 전체 `db push`를 실행하지 않습니다.

적용 뒤 점검 SQL을 다시 실행합니다. 사용자/관리자 권한, 동시 수정, 같은 공고·연락처 중복과 메일 트리거 동작은 실제 계정으로 따로 확인합니다. 새 AI 테이블에는 활성 예산이나 모델을 자동으로 넣지 않습니다.

## 3. AI 서버 함수만 별도 배포

`supabase/functions/growth-ai/`의 **index.ts, handler.ts, policy.ts 세 파일**이 함께 필요합니다. 앱의 main 병합만으로 Edge Function이 배포되지는 않습니다.

현재처럼 브라우저로 진행할 때는 이 세 파일을 합친 **`supabase/deploy/growth-ai-dashboard.ts`** 전체를 사용합니다. 원본 로직을 유지하고 내부 import만 제거한 파일이며 키는 포함하지 않습니다.

1. 대상 프로젝트 → **Edge Functions → Deploy a new function → Via Editor**.
2. 함수 이름을 정확히 **growth-ai**로 입력하고 새 함수의 **index.ts** 예제 코드 전체를 배포물 내용으로 교체합니다.
3. JWT 검증 기본값(켜짐)을 유지하고 **Deploy function**을 누릅니다. 기존 다른 함수의 코드를 수정하지 않습니다.
4. 배포 성공 화면/함수 URL을 확인합니다. 사용자는 배포를 마쳤다고 알렸고, 이어 Test에서 POST `{}`에 HTTP 401/`로그인이 필요합니다.`가 나온 화면을 제공했습니다. 배포된 코드의 차단 응답을 확인했으므로 단순 재배포를 반복하지 않습니다.
5. Secrets에서 `ANTHROPIC_API_KEY` 설정 존재 여부를 확인합니다. 있으면 기존 설정을 유지하고, 없으면 관리자가 기존 Claude API 키를 Supabase의 비밀 값 입력란에 직접 등록합니다. 값을 코드·채팅·캡처에 넣지 않습니다.

사용자가 키가 이미 있다고 확인했으며 기존 키를 유지합니다. 401 응답만으로 유료 호출 성공을 판단하지 않았습니다. 이후 로그인한 앱에서 Haiku의 `연결 성공` 응답과 완료 비용 안내를 제공해 실제 호출·정산 성공을 확인했습니다. 키 값은 전달받거나 기록하지 않았습니다.

배포물은 `node scripts/build-growth-ai-dashboard.mjs`로 생성하고 `node scripts/build-growth-ai-dashboard.mjs --check`로 원본 일치를 확인합니다. 변경 시 원본 세 파일을 수정한 뒤 재생성하며 배포물만 직접 수정하지 않습니다. 저장소에서 원본과 배포물 이력을 함께 관리합니다. 이전 배포에서 전체 167개 테스트와 배포물 Deno 검사 통과.

공식 대시보드 절차: https://supabase.com/docs/guides/functions/quickstart-dashboard . 비밀 설정: https://supabase.com/docs/guides/functions/secrets .

배포 환경에 Supabase CLI 인증이 준비된 경우 `erp`에서 실행합니다.

```sh
supabase functions deploy growth-ai --project-ref hophgcpszenrvchvbkav
```

플랫폼 JWT 검증 기본값은 유지합니다. 함수 내부에서도 로그인 사용자를 확인하고 DB에서 활성 구성원/예산을 다시 검증합니다. 공개 함수로 바꾸거나 service role 키를 프런트엔드에 넣지 않습니다.

`ANTHROPIC_API_KEY`는 프로젝트 서버 비밀 설정의 기존 키를 사용합니다. 설정 여부만 확인하고 값을 대화·저장소·로그에 기록하지 않습니다. 키가 없으면 함수는 설정 안내를 반환합니다.

배포 뒤 비용 없는 차단 경로부터 확인합니다. 비로그인 요청이 거부되는지, 잘못된 요청이 거부되는지, 미설정 예산 상태에서 실행이 막히는지 확인합니다. 실제 잔액·크레딧 기간·다른 업무 사용액과 배정 한도 확인 전에는 유료 시험을 실행하지 않습니다.

공식 문서: [배포](https://supabase.com/docs/guides/functions/deploy), [함수 인증](https://supabase.com/docs/guides/functions/auth).

## 4. 웹 배포와 사용 점검

PR #354는 main에 병합되었고 Cloudflare 운영 배포 체크 성공을 확인했습니다. 후속 웹 보완은 새 변경의 테스트·타입 검사·빌드와 해당 커밋의 배포 체크를 확인합니다. 웹 배포와 DB/함수 적용 근거를 구분해 기록합니다. 비용·기록 갱신 점검은 기존 요청을 조회하며 새 유료 호출을 만들지 않습니다.

- 관리자/일반 팀원, PC/모바일에서 등록→저장→검수→연결 흐름을 확인합니다.
- 콘텐츠에서 선택한 광고 캠페인이 정확히 열리는지 확인합니다.
- 공고 마감은 한국시간으로 저장·재표시되는지 확인합니다.
- 기존 Gmail 동기화 결과가 연락처 검토함에 들어오며 제외·중복 후보가 되살아나지 않는지 확인합니다.
- 실제 화면과 `/manual/growth.html` 사용설명을 대조합니다.

인스타 계정 자동 수집·나라장터 공식 API 수집·매체 자동 배포/광고 집행은 별도 계정 권한과 실행 결과 검증이 남아 있습니다. 지금 구현한 수동 등록·자료 추출·검수·발행 기록을 자동 연동 완료로 보고하지 않습니다.

오류 발견 시 웹을 이전 검증 버전으로 돌리는 것과 새 DB 데이터를 삭제하는 것은 구분합니다. 고객 기록과 설치 이력을 지우지 않습니다. 기존 meeting-minutes 배포와 Supabase 사용량 점검도 별도로 남아 있습니다.
