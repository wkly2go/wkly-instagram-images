> **2026-11-13 갱신:** `gmail` 운영 배포와 코드 일치, 기존 인증 설정 유지, GET 405를 확인했습니다. 기존 10분 예약은 활성 상태이며 수동 동기화는 실행하지 않았습니다. 아래 11/12 배포 대기 문구는 과거 기록입니다. [최신 배포 기록](SERVER_DEPLOYMENT_20261113.md)을 우선합니다.

2026-11-12. 프로젝트 **hophgcpszenrvchvbkav**, 기존 함수 **gmail** 대상입니다. 이번 작업은 코드·단일 파일 준비 및 모의 검증이며 **운영 Gmail 호출, DB 변경, 함수 배포는 실행하지 않았습니다.** 웹 배포만으로 서버 함수가 바뀌지는 않습니다.

## 변경한 동작

- 한 번에 최대 20페이지(페이지당 최대 500개 목록)를 확인하고, 상세 조회는 전체 최대 400건으로 제한합니다. 상한에 닿으면 완료로 표시하지 않고 pending 상태와 체크포인트를 남깁니다.
- 조회 시작·끝 시각을 고정하고 페이지 토큰·현재 페이지의 미처리 ID를 기존 app_settings에 저장합니다. 해당 페이지의 저장을 확인하기 전에는 다음 페이지로 넘어가지 않습니다.
- 실패·미처리 ID는 다음 실행에서 이어갑니다. DB 조회가 실패하면 모든 메일을 새 메일이라고 간주하지 않고 중단합니다. 저장 응답이 유실돼도 이미 저장된 ID를 다시 확인하며 기존 행을 덮어쓰지 않습니다.
- 주동기화·과거 자료는 gmail_sync, 최근 2일 새로고침은 gmail_refresh 키를 사용합니다. 새로고침이 진행 중인 과거 자료 수집을 지우지 않습니다.
- 진행 저장에는 체크포인트 ID 조건을 사용해 오래된 실행이 새 진행 상태를 덮어쓰지 못하게 합니다. 충돌은 오류로 알리며 잠시 후 재시도합니다.
- 상태 응답은 처리량·대기·실패 건수만 제공합니다. 페이지 토큰과 미처리 메일 ID를 상태 화면에 보내지 않습니다.

새 테이블이나 마이그레이션이 필요하지 않습니다. **0107·0113·0114·0115 및 기존 Gmail SQL을 재실행하거나 전체 db push를 하지 않습니다.**

## 배포 파일 준비

erp 디렉터리에서:

    npm run build:gmail-dashboard
    node scripts/build-gmail-dashboard.mjs --check
    npm run test:gmail

원본은 supabase/functions/gmail/sync.ts, index.ts입니다. 대시보드용 파일은 [supabase/deploy/gmail-dashboard.ts](../supabase/deploy/gmail-dashboard.ts)입니다. 원본 변경 후 생성기를 다시 실행하고, 생성 파일만 따로 수정하지 않습니다.

1. 대상 프로젝트의 기존 **gmail** 함수와 현재 배포 버전을 확인합니다.
2. 대시보드 편집기의 index.ts에 생성 파일 전체를 넣습니다. 원본 index.ts만 복사하면 sync.ts가 빠집니다.
3. 기존 인증 설정과 Secrets·Vault 연결을 유지합니다. 키나 토큰 값을 문서·대화·스크린샷에 복사하지 않습니다. 이미 설정된 예약 호출의 인증 방식을 임의로 바꾸지 않습니다.
4. 실제 배포 시 함수 이름·버전·배포 성공·시각을 기록합니다. 단일 파일을 준비한 것과 실제 서버 배포를 구분합니다.

## 실제 호출과 기존 첨부 처리의 구분

Gmail 메일함은 읽기만 하며 메일 발송·삭제·라벨 수정은 하지 않습니다. 그러나 기존 함수에는 **Drive 수신방으로 첨부를 복사하는 기능**이 있습니다. 예약용 x-sync-key 경로는 동기화 뒤 첨부 저장을 실행하고, 관리자 files 동작도 Drive에 파일을 생성합니다. 이번 보완에서 이 기존 기능·정책을 바꾸지 않았습니다.

따라서 예약 키·관리자 sync·refresh·files 호출을 단순 연결 시험으로 실행하지 않습니다. sync·refresh는 운영 DB에 메일 및 연락처 후보를 저장할 수 있습니다. files·예약 호출은 Drive 저장까지 발생할 수 있습니다. 함수 배포 후 이미 활성인 예약이 새 코드를 실행할 수도 있으므로 기존 예약 상태와 운영 검증 범위를 함께 기록합니다.

변경 없는 확인은 OPTIONS(함수 본문 기준 200), GET(405), Authorization 없는 POST(401)로 제한합니다. 플랫폼 인증이 먼저 차단하면 본문의 응답과 다를 수 있으며, 시험을 위해 인증을 끄지 않습니다. 새 테스트는 이 경로가 DB·Gmail·Drive를 호출하지 않는지 모의 환경에서 확인합니다.

## 남은 확인과 복구 원칙

- 기존 10분 예약 wkly_gmail_sync, 회사 구글 계정의 읽기 권한·실제 실행 결과는 운영 확인 전입니다. SQL 파일 존재가 예약 설치·최근 성공을 증명하지 않습니다.
- 저장된 메일이 연락처 후보가 되는 과정은 기존 growth_mail_capture·growth_mail_backfill 트리거입니다. 이번 보완은 이 SQL을 재설치하지 않습니다.
- pending=true이면 해당 조회 구간을 다 끝낸 상태가 아닙니다. failed>0은 상세 조회 등 확인하지 못한 건이 남았다는 뜻이며 전체 메일 실패로 해석하지 않습니다.
- 영구 삭제된 메일의 404, 계속 실패하는 응답, 만료된 페이지 토큰 등은 관리자 확인 대상입니다. 실패 ID를 자동으로 버리거나 다음 페이지로 건너뛰지 않으므로 해당 페이지의 수집이 대기할 수 있습니다. 기록·체크포인트를 지워 해결했다고 처리하지 않습니다.
- 고정 구간을 끝낸 뒤 다음 주동기화는 마지막 완료 시각보다 하루 겹치게 조회합니다. 새로 들어온 메일을 이전 구간 완료로 표시하지 않습니다.
- 모의 Google 응답·실제 Supabase SDK 요청 검사는 운영 계정의 권한·할당량·실제 데이터 처리 검증을 대신하지 않습니다. 배포와 실계정 검증은 각각 결과를 확인한 뒤 완료로 표시합니다.
